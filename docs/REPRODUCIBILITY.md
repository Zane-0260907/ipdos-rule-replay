# Rule replay demonstrator: scope and reproduction

## What was implemented

This is a narrow software engineering demonstrator around three existing IPDOS rule groups: sales forecast, traffic forecast, and menu adjustments. It adds fixed synthetic input snapshots, frozen evaluation times, immutable named policy profiles, explicit test oracles, traces for both triggered and clear rules, policy/output differences, and complete JSON exports. The web UI is new. It does not claim these facilities existed in the public baseline.

Normal API calls retain the registry's previous default thresholds. The replay interface alone selects candidate profiles. The separate replay NestJS module does not depend on Prisma or the original backend's mutable fixture store or in-memory simulation history.

## Contracts and injected regression

All ten inputs are synthetic; `SYNTHETIC-001` is an invented store identifier. The evaluation time is always `2026-10-21T12:00:00.000Z`. Inputs and expected IDs are checked in at `src/replay/replay-fixtures.ts`. Oracles are authored explicitly from the documented comparisons below, not generated by calling the evaluator.

| Scenario         | Expected behavior under `registry-v1`                                                     |
| ---------------- | ----------------------------------------------------------------------------------------- |
| `traffic-eight`  | Eight flat traffic points satisfy the minimum; no warning                                 |
| `traffic-three`  | Three flat points trigger `predictions.traffic.low-resolution`                            |
| `traffic-age-12` | Exactly twelve hours is accepted; no stale warning                                        |
| `traffic-age-13` | Thirteen hours triggers `predictions.traffic.snapshot-staleness`                          |
| `sales-clean`    | Fresh, no shortage and no critical SKUs; no warning                                       |
| `sales-gap-15`   | Gap equals threshold 15: no shortage escalation; 1/5 critical density triggers            |
| `sales-gap-16`   | Gap 16 exceeds threshold 15: shortage escalation and density trigger                      |
| `sales-age-25`   | Twenty-five hours triggers `predictions.sales.snapshot-staleness`                         |
| `menu-clean`     | Five items, no restock or conflict; no warning                                            |
| `menu-conflict`  | The same ingredient is promoted/suppressed, with restock 5: restock and conflict warnings |

`registry-v1` preserves the actual baseline values: sales maximum age 24 h, traffic maximum age 12 h, minimum 8 traffic points, shortage threshold `max(10, totalDemand * 0.15)`. Other rules in these three groups are unchanged. Each scenario runs all three rules in its group, giving 30 rule evaluations per policy (nine distinct rule definitions overall). Not every rule is exercised in its triggering state; this is not exhaustive rule or application coverage.

`sparse-v2-seeded-regression` deliberately changes only `minTrafficPoints` from 8 to 3. The original `traffic-three` oracle remains unchanged. Its missing low-resolution warning is therefore detected as a candidate contract failure. This is an executable injected regression, not evidence of an observed historical incident. The remaining nine scenarios provide a small change-isolation check; they do not establish general sensitivity or false-positive rates.

## Repeat and export semantics

The evaluator reads no wall clock, random source or database. A replay bundle contains the complete scenario and expected IDs, policy ID and parameters, all rule checks with full `RuleHit` details, actual IDs, missing/unexpected IDs, pass/fail, and three SHA-256 identities. Snapshot and policy hashes bind their respective content; the content hash binds the full output excluding the hash field itself. JSON object keys are sorted recursively when hashing; array order is preserved. These hashes identify content and do not authenticate it.

`npm run replay:evidence` runs the whole suite, then checks 100 repeated suite executions for byte-identical canonical JSON. `npm run replay:verify -- <export.json>` starts a separate process, re-executes a built-in scenario/profile and checks the complete exported content, detecting edits or version mismatch. An expected candidate failure still verifies successfully if faithfully reproduced. Export verification accepts only this version's checked-in synthetic catalog; arbitrary snapshot import and persistent run storage are outside this demonstrator.

The comparison reports full parameter changes, added/removed warning IDs and changed hit details. Oracles currently assert the exact warning-ID set, not every numeric field or downstream business decision. The rule trace is evaluation evidence, not a production audit trail.

## Commands

```sh
npm ci --ignore-scripts
npm run prisma:generate
npm run build
npm test -- --runInBand
npx --no-install ts-node scripts/baseline-compatibility.ts
npm run replay:evidence
npm run replay:verify -- artifacts/seeded-regression.json
npm run demo
# In another terminal, with Chrome/Edge/Chromium installed:
npm run test:ui
```

Use the repository root as the working directory. On the managed Windows runner, Jest's temporary-directory resolution and HTTP/browser loopback access required approved execution outside the filesystem/network sandbox. The application needs no elevated OS privileges on an ordinary local developer machine.

## Evidence and permissible interpretation

`artifacts/replay-evidence.json` records actual suite counts, repeats, source byte hashes, runtime and base commit. `artifacts/replay-suite.json` contains the full comparison results, and `artifacts/seeded-regression.json` is a portable example export. `artifacts/ui-evidence.json` and PNGs are produced by an actual installed Chromium browser; they do not mock the interface. Machine-local caches, browser profiles and test database files are ignored under `artifacts/local/`.

Re-running after changes may produce different content hashes. Regenerate evidence only after testing the final source and inspect changed outputs rather than copying old results into a paper. Source-byte hashes may change with line endings; semantic replay hashes use canonical JSON. The Git base identifies the starting point; source hashes distinguish the changed implementation before publication.

These results support only the statement that this small synthetic contract suite reproduces one deliberately injected threshold regression and provides deterministic replay under the tested environment. They do not support forecasting accuracy, optimization quality, causal effects, real-store benefits, persistent audit guarantees, production deployment claims, or superiority over existing testing tools.
